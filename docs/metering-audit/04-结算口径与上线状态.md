> 状态日期：2026-09-03。本文是内部草案，需负责商务/合同的人确认后才能对外使用。

## 1. 建议结算口径

双方确认：费用结算以 Azure 官方 Cost Management 最终入账数据为准，AnyRouters 站内用量用于近实时查询和运营参考。因账单延迟、缓存读写、流式中断、失败请求或上游重试产生的可解释差异，按月对账、多退少补；完整结算周期的差异率超过 3% 时，双方先按日、Azure 资源和 deployment 核对原因，再确认调整金额。

如某组 Azure 资源并非某一客户独占，不得宣称“Azure 订阅导出就是该客户全部用量”；必须以资源/deployment 和站内渠道映射后的数据结算。

## 3. 对账口径

- 时区：UTC；日区间为左闭右开。
- 主键：`日期 + Azure 资源 + ModelDeploymentName`。
- 输入 token：站内 `tokens_prompt_total` 对 Azure `InputTokens`，两者都包含 cached token。
- 输出 token：站内 `tokens_output` 对 Azure `OutputTokens`。
- 缓存费用：使用响应里的 `cached_tokens` / `cache_write_tokens` 和 Azure Cost 明细单独核对。
- 延迟：最近 48 小时只做预览，T+2 后再判断是否超过 3%。
- 安全：仅导出按日/渠道/模型的聚合数，不导出 prompt、用户名、Key、邮箱或连接串。

## 4. 上线前验收条件

1. 振川渠道 3/4 的模型都能归属到正确 Azure 资源和 deployment，无 `mapping_missing`。
2. 连续生成 7 个完整 UTC 日的站内与 Azure 报表。
3. T+2 数据中，超过 3% 的条目能归因到缓存、失败、重试、中断、漏映射或账单延迟。
4. 任务只有数据库读权限；失败不会修改用户额度、价格、渠道或 Azure 资源。
