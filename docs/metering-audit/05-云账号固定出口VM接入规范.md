# 云账号固定出口 VM 接入规范（Azure / GCP）

> 最后更新：2026-09-03。适用于 AnyRouters（AN）接入新的 Azure、GCP 或其他云厂商账号。

## 1. 隔离原则

- 隔离单位是“云账号 / 结算主体”，不是单个模型：同一账号下的多个模型与资源可以共用该账号专属出口；不同账号不得共用同一出口 IP。
- 每新增一个 Azure 或 GCP 账号，必须先建立该账号专属的出口 VM 和静态公网 IP，再接入对应渠道。
- Azure 账号的出口 VM 原则上建在该账号自己的 Azure 订阅中；GCP 账号的出口 VM 原则上建在该账号自己的 GCP 项目中。
- 不同云账号不得复用 VM、公网 IP、代理凭据或渠道标签。
- 固定出口用于权限隔离、故障定位和审计，不代表云厂商无法从其他信息识别账号关联，也不能代替平台合规要求。
- 账号、API Key、代理密码和连接串只放 Secret Manager、Key Vault 或 AN 密钥配置，不写入 Git、Notion、聊天或普通日志。
- 未实际启用的账号不提前创建 VM，避免持续产生计算、公网 IP 和流量费用。

## 2. 标准命名

| 资源 | 命名模板 |
|---|---|
| 资源组 / 项目标签 | `rg-anyrouters-egress-<account-label>` |
| VM | `vm-anyrouters-egress-<account-label>-01` |
| 公网 IP | `pip-anyrouters-egress-<account-label>-01` |
| 网络规则 | `nsg-anyrouters-egress-<account-label>-01` |
| AN 渠道标签 | `upstream:<provider>:<account-label>` |

`account-label` 只用内部代号，不使用邮箱、姓名或客户敏感信息。

## 3. 标准接入流程

### 3.1 接入前确认

- [ ] 明确云厂商、账号 / 租户 / 订阅或项目、结算主体、所需模型与区域。
- [ ] 确认该账号没有复用其他账号的出口 VM 或公网 IP。
- [ ] 记录 AN 渠道 ID、上游资源名、deployment / model 名和当前配额。
- [ ] 确认回滚方式：禁用新渠道或清空该渠道的代理配置即可恢复原链路。

### 3.2 创建专属出口

- [ ] 在该账号自己的订阅 / 项目中创建独立资源组或带独立标签的资源。
- [ ] 选择满足代理吞吐量的最小 VM 规格；先小规格上线，根据 CPU、连接数、带宽和延迟监控决定是否扩容。
- [ ] 创建并绑定静态公网 IPv4，禁止使用会随重启变化的临时公网 IP。
- [ ] 配置代理服务。当前实现可使用 Squid HTTP CONNECT；使用其他代理前需先确认 AN 支持。
- [ ] 同 VNet 时优先只监听私网地址；跨 VNet / 跨账号时使用 VPN、对等连接，或在公网监听时同时启用源 IP 白名单、强认证和最小端口开放。
- [ ] 禁止开放匿名代理；管理端口只允许运维来源访问。

### 3.3 接入 AN

- [ ] 将代理凭据放入安全配置，不写入文档。
- [ ] 在对应渠道的 `proxy` 字段填入该账号专属代理地址。
- [ ] 同一账号的多个渠道可以指向同一专属出口；其他账号不得指向此出口。
- [ ] 保存渠道后确认旧 HTTP 客户端连接池已重建。
- [ ] 新渠道先保持低优先级或测试状态，不直接承担全部流量。

### 3.4 验收

- [ ] 通过代理查询公网出口，结果必须等于该账号登记的静态公网 IP。
- [ ] 对上游执行最小真实调用，确认响应成功、deployment 正确且无 401 / 403 / 429。
- [ ] 检查代理访问日志，确认请求只到达该账号对应的 Azure / GCP 上游域名。
- [ ] 做反向检查：其他账号的渠道不得命中这个出口 IP。
- [ ] 观察错误率、429、延迟、VM CPU / 内存 / 网络和并发连接；通过后再逐步提升优先级和权重。
- [ ] 把账号标签、VM、静态 IP、渠道 ID、验证时间和回滚点写入 AN 开发日志；不得记录密钥。

### 3.5 回滚与停用

1. 先禁用新渠道或恢复上一份渠道配置。
2. 清空或改回该渠道的 `proxy`，确认流量不再经过新 VM。
3. 验证 AN 状态接口与代表性模型。
4. 观察期结束前保留 VM 和静态 IP；确认无回流后再停机或删除。
5. 删除前再次核对资源名、账号归属和备份，不做跨资源组批量删除。
