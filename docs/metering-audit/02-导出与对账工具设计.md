# 站内日级导出与离线对账工具设计（第一阶段 · 任务 2/3）

> 设计依据：`01-计量链路审计报告.md` + 对 LiteLLM / OpenMeter / Langfuse / one-api 生态与 Azure 官方文档的调研。
> 原则：只读、离线、可重跑、不引入定时任务与生产依赖、不改任何扣费逻辑。

## 1. 形态

一个独立 CLI：`cmd/usagetool`，两个子命令，均不依赖运行中的网站进程：

```bash
# 任务2：站内日级导出（只读扫 logs 表）
usagetool export --db-type sqlite --dsn ./new-api.db \
  --from 2026-08-01 --to 2026-09-01 --tz UTC \
  --channel-map channel_map.yaml --out site_daily.csv

# 任务3：离线对账（纯文件输入，不连数据库）
usagetool reconcile --site site_daily.csv \
  --azure azure_export.csv --mapping azure_mapping.yaml \
  --out report/
```

## 2. 关键设计决策（与调研结论的对应）

| 决策 | 依据 |
|---|---|
| 对账主键 = `UTC日 × deployment`（渠道→部署名映射由运营方配置提供） | Azure Monitor token 指标维度**只有 ModelDeploymentName 没有 ModelName** |
| 缓存 token 差异只与 Cost CSV 的 cached meter 对账，不与 Monitor 指标对账 | Azure Monitor **没有缓存 token 指标** |
| Azure 列名全部走 YAML 配置映射，内置 profile 但不硬编码 | EA / MCA / 老 PAYG / FOCUS 四套列名互不相同 |
| 日切在 Go 侧用 `--tz`（IANA 名）折算，SQL 零日期函数 | 三库时区函数语义不一致（one-hub 硬编码 +8h 是反面教材）；Azure 全链路 UTC，对账默认 UTC |
| token 细类按互斥桶输出（input 不含 cache），另给 total 校验 | Langfuse `usage_details` 口径；避免 LiteLLM cached 未扣减的已知 bug |
| 成功/失败/退款请求分列（type=2/5/6），计费口径=成功 | Azure「4xx 内容过滤仍计费、429 不计费」，需要请求数分层比对 |
| `other` JSON 在应用层容错解析，未知键入 `tokens_other` | logs 表 token 细类只存在于 JSON，schema 随版本漂移 |
| 导出附 manifest（参数、水位、行数、版本），同参数重跑逐字节一致 | 可复核性；迟到数据靠重跑解决，不做增量状态 |
| 差异率分母为 0 输出 `N/A`；缺数据输出 `未提供` 而非 0；归属不明进 `待核对` | 运营方既有《核算与计算规则》第 4/6 条 |

## 3. 站内导出（canonical daily usage v1）

数据源：`logs` 表，`type IN (2,5,6)`，按 `created_at` 范围 + `id` 分页扫描（只读）。

列（同时是对账工具的站内侧输入格式）：

```
date, channel_id, channel_name, account_label, azure_resource, deployment,
model_upstream, model_site,
requests_success, requests_error_logged, requests_refund, retry_attempts, client_disconnected,
tokens_input, tokens_output, tokens_cache_read, tokens_cache_write,
tokens_audio_input, tokens_audio_output, tokens_image, tokens_other,
rows_local_estimated, rows_cache_write_estimated, rows_zero_usage,
quota, amount_usd
```

说明：
- `model_upstream` 优先取 `other.upstream_model_name`（模型映射后的真实上游名），`model_site` 为站内展示名。
- 互斥桶换算：非 Claude 语义时 `tokens_input = prompt - cache_read - cache_write`（截断非负）；`other.usage_semantic=="anthropic"` 时 prompt 本身即纯输入。
- `requests_error_logged` 依赖 `ERROR_LOG_ENABLED=true`；默认 false 时恒为 0，工具在 manifest 中标注该口径缺口（审计报告 §7）。
- `retry_attempts = Σ max(0, len(admin_info.use_channel)-1)`；`client_disconnected` 计数 `stream_status.end_reason=="client_gone"`。
- usage 来源三计数：`rows_local_estimated`（`admin_info.local_count_tokens`）、`rows_cache_write_estimated`（GPT-5.6 128 块估算标记）、`rows_zero_usage`（prompt+completion 均为 0 的消费日志）。审计已证明打标覆盖不全（§6），这三列是"下界"，manifest 注明。
- `quota` 为站内原始整数；`amount_usd = quota / 500000`，仅展示换算，两列并存不混淆。
- `account_label / azure_resource / deployment / channel_name` 来自 `--channel-map` YAML（运营方提供，渠道 ID → 标签），缺省为空并计入 `待核对`。

## 4. 对账工具

输入：站内 canonical CSV + Azure 导出（CSV）+ `azure_mapping.yaml`。

映射配置支持两种形状：
- **宽表**（Azure Monitor 指标导出后整形）：每行自带 input/output/cache_read token 列；
- **长表**（Cost Management CSV）：每行一个 meter，配 `meter_rules` 正则把 `MeterName` 解析成方向（in/out/cache_in）与模型，`Quantity × unit_scale` 折算 token。

```yaml
format: wide            # wide | meter_long
date_column: Date
date_formats: ["2006-01-02", "01/02/2006"]
key: deployment          # deployment | model | resource
key_column: ModelDeploymentName
columns:                 # wide 形状
  input_tokens: InputTokens
  output_tokens: OutputTokens
  requests: Requests
  cost: CostInBillingCurrency
unit_scale: 1            # 每单位 Quantity 折算的 token 数（Cost meter 常为 1M）
meter_rules:             # meter_long 形状
  - match: "(?i)\\bin\\b.*cach|\\bcd\\b"
    direction: cache_read
  - match: "(?i)\\bin(p|put)?\\b"
    direction: input
  - match: "(?i)\\bout\\b"
    direction: output
site_key: deployment     # 站内侧用哪一列做 join key
```

输出 `report/`：
- `reconcile_report.csv`：每行 `日期 × key × 指标`，含 站内值、Azure 值、绝对差、差异率 `(站内-Azure)/Azure`、绝对差占比、原因标签；
- `reconcile_summary.md`：总量核对、按标签汇总、超阈值（默认 3%）条目清单。

边界处理（全部有测试）：
- 分母 0 → 差异率 `N/A`，不判红；
- 单侧缺失 → `mapping_missing`（键无映射）或 `未提供`（该日该侧无数据），不得记 0；
- 重复键行 → 合并累加并打 `duplicate_rows_merged` 警示；
- Azure 侧最近 48h 内的日期 → 附 `timezone_or_late_arrival` 软标签（Cost 摄取延迟）；
- `ChargeType=Refund/RoundingAdjustment` 行单列，不计入差异率。

自动原因标签（与任务书清单对应）：`upstream_usage_missing`、`local_estimate_used`、`client_disconnected`、`retried_on_another_channel`、`cache_usage_estimated` 由站内行的计数列触发；`timezone_or_late_arrival`、`mapping_missing`、`unknown` 由对账过程触发；`transport_failed_before_response`、`upstream_may_have_billed` 在 `requests_error_logged>0` 或站内显著小于 Azure 时提示。

## 5. 需要运营方提供/执行的配置（届时给步骤清单）

1. Azure Monitor 指标导出（`az monitor metrics list`，指标 `ProcessedPromptTokens`/`GeneratedTokens`/`AzureOpenAIRequests`，按 `ModelDeploymentName` 拆维度，粒度 P1D，UTC）；
2. Cost Management 日粒度导出（含 MeterName/Quantity/Cost 列）；
3. `channel_map.yaml`：渠道 ID → account 标签 → Azure 资源 → deployment；
4. 时区口径确认（建议对账统一 UTC）；
5. 生产 `FORCE_STREAM_OPTION` / `RetryTimes` / `ERROR_LOG_ENABLED` 实际值。
