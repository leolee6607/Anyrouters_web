## 三、审计核心结论速查（对账时必须记得的事实）

1. **失败请求默认零留痕**：`ERROR_LOG_ENABLED` 默认 false → 失败 attempt 不落库，而 Azure 可能已计费。生产观察期建议开启（运营方决定）。
2. **客户端断开不一致**：Chat 流式按已收 token 扣费；Responses 流式全额退款（可被利用白嫖；也是 Azure>站内 的稳定来源）。第二阶段候选修复，未经确认不要动。
3. **Azure GPT-5.6 缓存写入 128 块本地估算**（`relay/common/gpt56_cache_billing.go`）：最大已知系统性偏差源，有 `cache_write_estimated` 标记可单独对账。
4. **分层计费 + 上游无 usage = 站内 0 扣费**（tiered 不填 ModelRatio 导致兜底=0）。第二阶段候选。
5. **对账主键必须用 Azure 资源 + deployment**：deployment 名只在单个 Azure 资源内唯一；跨资源只用 deployment 会串账。`InputTokens` 要与站内完整 `prompt_tokens` 对比（含缓存 token），缓存读/写计费再与 Cost 明细单独对账。
6. 日志表 token 细类只在 `other` JSON 里，SQL 无法直接聚合——导出工具已处理；`quota_data` 表无渠道维度，不能做对账数据源。
7. `RetryTimes` 默认 0；**不得擅自调高重试**（上游可能已计费，会重复费用）。
8. quota 是 int32 整数，500000 quota = $1；quota 和金额是两列，不能混作 token。
