# 计量链路审计报告（第一阶段 · 任务 1）

> 基线：`main` / `7ec0a59a`。本报告只做观察与归因，不改变任何扣费逻辑。
> 目的：为「站内用量 vs Azure 官方用量」对账提供代码级事实依据。
> 所有结论均附 `文件:行号` 证据，可直接跳转核对。

---

## 1. 总览：usage 的三种来源

站内每条消费日志的 token 数来源只有三类，但**目前没有统一的来源标记字段**：

| 来源 | 含义 | 现有标记 |
|---|---|---|
| `upstream_reported` | 上游（Azure/OpenAI）在响应中返回的 usage | 无正向标记（默认态） |
| `local_estimate` | 本地 tiktoken/字符启发式估算 | 仅部分路径写 `other.admin_info.local_count_tokens`（覆盖不全，见 §6） |
| `missing` | usage 完全缺失，quota 记 0 或按 1 token 兜底 | 仅 `usage==nil` 时日志拼入"上游无计费信息"文案 |

**这是对账差异的第一大结构性问题**：无法从存量日志可靠区分三种来源，导致差异无法自动归因。

## 2. 场景矩阵：Chat Completions

### 2.1 流式（SSE）

usage 提取：**只看最后一个 chunk**（音频模型看倒数第二个）。
`relay/channel/openai/relay-openai.go:125-186`、`relay/channel/openai/helper.go:118-144`

| 场景 | 上游是否可能计费 | 站内 usage | 是否退款 | 站内请求记录 | 重复扣费风险 |
|---|---|---|---|---|---|
| 正常返回，末 chunk 含 usage | 是 | 上游 usage | 差额结算 | 1 条消费日志(type=2) | 无 |
| usage 在倒数第二 chunk（后跟空帧） | 是（全额） | **静默降级为本地估算**（`relay-openai.go:177-180`） | 差额结算 | 1 条消费日志，**不打标** | 无，但 token 数偏差 |
| 上游全程未返回 usage | 是（全额） | 本地估算：prompt 用请求前估算值，completion 用累积文本 tiktoken（`service/usage_helpr.go:22-28`），tool call 每个 +7 token | 差额结算 | 1 条消费日志，打标 `local_count_tokens` | 无 |
| 客户端中途断开 | **是，Azure 可能继续生成并全额计费**（站内硬断连接不 drain，`relay/helper/stream_scanner.go:62-66`） | 按已收到部分结算（`relay-openai.go:186` 恒 return usage, nil） | 不退款 | 1 条消费日志，`other.stream_status.end_reason="client_gone"` | 无 |
| 流式 idle 超时（默认 300s，`STREAMING_TIMEOUT`） | 是（部分或全额） | 按已收到部分结算 | 不退款 | 1 条消费日志 | 无 |
| 上游连接失败（发出前） | 否 | 无 | **全额退预扣** | 默认**零记录**（`ERROR_LOG_ENABLED=false`，`common/init.go:152`） | 无 |
| 上游返回非 200 | **可能**（部分 4xx 上游已处理 prompt） | 无 | 全额退预扣（或重试） | 默认零记录 | 无 |

### 2.2 非流式

| 场景 | 上游是否可能计费 | 站内 usage | 是否退款 | 站内请求记录 | 备注 |
|---|---|---|---|---|---|
| 正常返回含 usage | 是 | 上游 usage | 差额结算 | 1 条消费日志 | 标准路径 |
| `prompt_tokens==0`（usage 缺失） | 是 | 本地补算并**回写给客户端**（`relay-openai.go:235-264`） | 差额结算 | 1 条消费日志，**不打标** | ⚠️ 覆盖 usage 时**丢弃 `prompt_tokens_details`（含 cached_tokens）** |
| `prompt_tokens>0` 但 `completion_tokens==0` | 是 | completion 按 0 计费，不补算 | 差额结算 | 1 条消费日志 | 站内必然少记 |
| usage 整体为 nil | 是 | prompt 用估算值，quota 可能为 0（`service/text_quota.go:197-202`） | 差额退回 | 1 条 quota=0 日志 +"上游无计费信息" | |
| 响应体解析失败 | **是（Azure 已完整生成）** | 无 | **全额退款** | 默认零记录 | 站内 0 vs Azure 全额 |
| 无超时挂起 | — | — | — | — | ⚠️ `RELAY_TIMEOUT` 默认 0 = 非流式对上游**无超时**（`common/init.go:104`） |

## 3. 场景矩阵：Responses API

usage 提取：逐事件匹配 `response.completed`/`response.incomplete`（`relay/channel/openai/relay_responses.go:112-136`），比 Chat 的"只看最后一帧"稳健；但整条路径**不调用 `applyUsagePostProcessing`**，拿不到非标准 cached_tokens 兜底。

| 场景 | 上游是否可能计费 | 站内 usage | 是否退款 | 备注 |
|---|---|---|---|---|
| 流式正常 | 是 | 上游 usage（terminal 事件） | 差额结算 | 不强制也不需要 stream_options |
| 流式未见 terminal 事件（含**客户端断开**） | **是，可能已全额计费** | 无 | **返回 499 全额退款、零扣费、无消费日志**（`relay_responses.go:151-166`） | ⚠️ **与 Chat 流式行为相反**：同样的断开，Chat 收钱、Responses 全免。对 Responses-only 客户端是可利用的白嫖路径，也是对账时 Azure>站内 的稳定来源 |
| 流式 usage 为 0 | 是 | completion 补文本估算、prompt 补请求估算（`relay_responses.go:169-183`） | 差额结算 | **不打标** |
| 非流式 usage 为 nil | 是 | **usage 全 0，无任何回退估算**（`relay_responses.go:46-57`） | 差额全退 | ⚠️ 计费盲区，站内 0 vs Azure 全额 |

三条桥接路径（Chat↔Responses 互转）各有独立 usage 语义，对账下钻时需按 `other.request_conversion` 区分（`service/log_info_generate.go:220-246`）。

## 6. 「上游 vs 本地估算」标记覆盖缺口（对账工具需知）

`other.admin_info.local_count_tokens` 目前**只在 2 个写入点**（`service/usage_helpr.go:23`、`audio.go:58`）。以下 6 个本地估算/兜底路径**不打标**，对账时无法从日志区分：

1. 非流式 Chat 本地补算（`relay-openai.go:236-250`）
2. Responses 流式回退（`relay_responses.go:169-183`）
3. Responses 非流式 usage 缺失（静默 0，`relay_responses.go:48`）
4. 图片无 usage 强制 1 token（`image_handler.go:136-141`）
5. STT 回退（`audio.go:143-146`）
6. Realtime 本地估算（`relay_realtime.go:79-82,152-156`）

**第一阶段建议**（不改扣费，只加观察字段）：把 usage 来源提升为统一枚举（`upstream`/`local_estimate`/`missing`/`partial`）写入 `other.admin_info`，在上述回退点统一落标。

## 7. 重试与失败留痕

- `RetryTimes` 默认 **0**（`common/constants.go:153`），仅后台可配（上限 10），重试无退避。
- 重试换渠道；**预扣只做一次（循环外），最终失败全额退一次**（`controller/relay.go:170,176-185`），不存在 N 次预扣。
- **消费日志全程只 1 条且仅成功时写**；失败 attempt 需 `ERROR_LOG_ENABLED=true` 才落 type=5 错误日志（**默认 false → 失败零留痕**），且 token/quota 硬写 0（`model/log.go:252-258`）。
- attempt 序号无显式字段，只能用 `len(other.admin_info.use_channel)` 反推。
- 429：会触发重试（在默认重试区间 409-499 内），不会因状态码禁用渠道；但若开启自动禁用，OpenAI 429 的 `"You exceeded your current quota"` 文案会命中关键词表误禁（`setting/operation_setting/operation_setting.go:8-16`）。
- **同一请求所有 attempt 共享一个站内 `request_id`**（`middleware/request-id.go:21-29`），可聚合；但 `upstream_request_id` 只认 `X-Oneapi-Request-Id`，**不读 Azure 的 `apim-request-id`** → 对 Azure 恒为空，无法逐请求对账（`relay/channel/api_request.go:526-528`）。

**对账含义**：首渠道失败重试成功时，Azure 侧第一个账号可能已计 prompt token，而站内只有一条挂在最终渠道上的成功日志 → 差异标签 `retried_on_another_channel` + `upstream_may_have_billed`。

## 8. 结算/退款要点（影响对账口径）

- 预扣 → 结算 → 退款主路径：`BillingSession`（`service/billing_session.go`），Settle/Refund 均幂等。
- 信任旁路：余额充足用户预扣为 0（`billing_session.go:288-321`）。
- 钱包结算**保底为零**：扣不动的部分记 `shortfall` 不为负（`model/user.go:1049-1092`）。
- 日志存 **quota（int32，500000 quota = $1）**，不是金额（`common/constants.go:62`）。
- ⚠️ **分层计费模型 + 上游无 usage = 站内 0 扣费**：tiered 路径不填 `ModelRatio`，`usage==nil` 时跳过 tiered，兜底算出 quota=0 且预扣全退（`service/text_quota.go:406-420`、`relay/helper/price.go:347-351`）。Azure 侧则已全额计费——**对账时这是"Azure 远大于站内"的稳定来源之一**。

## 9. 站内现有聚合能力（导出工具的地基）

- `logs` 表：token 只有 `prompt_tokens`/`completion_tokens` 两列，**缓存/图片/音频 token 全在 `other` JSON 里**，SQL 无法直接聚合 → 日级导出需解 JSON。
- `created_at` 为 Unix 秒（UTC），日切需按运营方时区折算。
- `quota_data` 表：小时粒度预聚合（user×model），但**无渠道维度**，且默认开关 `DataExportEnabled` 控制，非原子 upsert 多实例可能重复计数（`model/usedata.go:75-87`）——**不适合做对账数据源**，对账应直接扫 `logs` 表。
- 渠道测试也写真实消费日志（`controller/channel-test.go:504`），对账需识别剔除或单列。
