## 剩余差额是什么

### Sol：主要在输出，证据指向长时间非流式调用的失败链路

同口径剩余 12.666695 USD，占该模型账单的 6.47698%。其中账单多出的输出 551,298 token 对应 11.025960 USD，约为该差额的 87.0%；普通输入、缓存写入、缓存读取分别贡献 0.839992、0.723615、0.077128 USD。

内部日志证据：

- Sol 的 653 笔非流式 Chat 成功调用产生 7,152,240 输出 token，最长 1,726 秒；222 笔流式 Responses 仅产生 130,618 输出 token，最长 46 秒。
- 渠道 3 的 38 次 unexpected EOF 和 7 次上游 408 都发生在 `/v1/chat/completions`；7 次 408 的总等待时间均约 1,740 秒（29 分钟）。另 3 次上游 500 也在 Chat 路径。这些历史失败日志缺少模型，不能把全部 48 次 Chat 错误直接分配给 Sol。
- 多次 EOF 在同一秒成批出现。9/24 00:08Z、22:49Z 的 Azure 单请求分钟桶分别报告 128,000 输出，9/27 13:05Z 报告 51,933 输出；各自的完整输入/输出向量在站点成功集合中找不到，时间落在稍后 EOF 批次中最长请求的执行区间。该证据支持“上游生成但站点未完成成功结算”的机制，不能代替逐请求计费明细。

因此，剩余差额的主要排查方向是长生成请求的连接中断/超时及成功记录集合缺失，不能据此再调整全站折扣。监控 Token 与账单 Token 本身也不完全一致，以上分钟桶不能直接累加为发票成本。

### Astra：客户端中断和缓存分类共同影响汇总

同口径净差额 1.0200385 USD，占账单 0.41033%。分类拆解为普通输入 +3.510380、缓存读取 +1.470421、缓存写入 −4.1487625、输出 +0.188000 USD。缓存写入的负差额抵消了其他分类的部分正差额；不能把净额全部说成“丢了输出”。

渠道共 45 次客户端中断全部在 Responses 路径。其中 44 次与 Astra 多出 HTTP 200 的小时计数吻合；9/24 额外 2 笔 HTTP 200 未增加 Token。支持客户端中断造成成功记录集合不同，但不能逐笔分配全部历史费用。

### 代理检查的边界

只读检查振川代理 VM `vm-anyrouters-egress-zhenchuan-01`：Squid 5.9，自 9/3 持续运行，服务 NRestarts=0；9/24–27 服务/内核日志未见重启或 OOM 记录。配置未显式设置 read/write timeout。Squid 文档给出的 read timeout 默认值是 15 分钟，但尚无对应历史 ERR_READ_TIMEOUT 记录证明它触发了本批 EOF；代理访问日志当前只保留到 9/28，无法回溯本窗口。因此没有修改代理超时，也不将“代理 15 分钟超时”写成已确认根因。

参考：[Squid read_timeout 定义](https://www.squid-cache.org/Doc/config/read_timeout/)。
